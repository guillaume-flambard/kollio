# Contributing to Kollio

Thanks for looking. Kollio is a small project with a strict delivery path: this page says how to run it, how a change is shaped, and what a commit has to carry. The product documentation is in French and the specifications, OpenSpec changes and code are in English.

## Run it locally

You need Node from `.nvmrc`, Python from `.python-version`, `pnpm`, `uv` and Docker.

```bash
cp .env.example .env
# set POSTGRES_PASSWORD and LITELLM_MASTER_KEY, generated locally, never committed
make install
make services
make migrate
make build
make up
```

`make verify` runs what continuous integration runs: lint, types, the API tests and the browser suite. Install Chromium once with `pnpm --dir apps/web exec playwright install chromium`. Integration tests need `TEST_DATABASE_URL` pointing at a separate database with the Alembic migrations applied. Anything that calls a model provider is opt in: set `KOLLIO_RUN_LIVE_EVALS=1` and the budget variables described in `docs/11-bootstrap-status.md`.

## The shape of a change

- One observable behavior per change. Agree on the scenarios first, then the boundary, then the implementation, then the evidence. `docs/12-delivery-workflow.md` is the full path and `AGENTS.md` lists the non negotiables.
- Scale the work to the risk. A copy correction does not need an architecture decision or a new test suite.
- Evidence lives with the change: browser assertions for a user journey, domain tests for deterministic rules, recorded evaluations for agent output. Never add a production authentication bypass for testing.
- The deterministic domain stays under unit test. A language model's prose is not unit tested; its output is validated against a schema and measured by a reviewed evaluation corpus.

## Commits and sign off

Every commit carries a Developer Certificate of Origin sign off, added with `git commit -s`. It certifies that you wrote the contribution or have the right to submit it under the project license. The text is at https://developercertificate.org.

Commit messages are conventional and fit on one line: `feat(web): ...`, `fix(api): ...`, `test(api): ...`, `docs: ...`, `chore(openspec): ...`. No body, no generated by trailer, no attribution footer. If a change needs a paragraph of explanation, that paragraph belongs in the change's `proposal.md` or `acceptance.md`, not in the commit.

## Reporting

Bugs and feature requests go through the issue templates. Security problems do not: see `SECURITY.md`. By taking part you agree to `CODE_OF_CONDUCT.md`.
