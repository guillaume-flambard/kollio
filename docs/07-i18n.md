# 07 — Multilingue FR / EN (dès le départ)

L'i18n rétro-fitté est un enfer → posé dès le scaffold. Deux mondes à séparer : **strings d'UI** et **contenu utilisateur**.

## 1. Strings d'UI
- **@nuxtjs/i18n** dès le départ : routing par locale, catalogues de messages (FR/EN) lazy-loadés.
- **Tout texte en clé de traduction**, jamais en dur (y compris dans les composants générés par Astra).
- Formats dates/nombres localisés.

## 2. Contenu utilisateur (idées, itérations, messages)
- Stocké avec sa **langue d'origine** (`lang` sur la ligne). **Jamais traduit en base par défaut.**
- **Traduction à la lecture, à la demande** : un agent LLM traduit à la volée pour l'affichage selon la locale du lecteur (avec cache).
- Les **agents répondent dans la locale de l'utilisateur** : la locale est un **paramètre de première classe** passé au graphe LangGraph (état du graphe).

## 3. Le point archi critique — embeddings multilingues
- Le matching idées↔personnes↔contributions = **le moat**. En embedding mono-langue, une idée FR et un profil EN ne matcheraient jamais.
- **Utiliser un modèle d'embedding multilingue / cross-lingual** (ex. `text-embedding-3-large` gère bien le cross-lingual, ou un modèle multilingue dédié). Une recherche EN retrouve une idée écrite en FR.
- Stocker `lang` sur les vecteurs ; l'espace vectoriel est partagé entre langues.

## 4. API
- **`Accept-Language`** de bout en bout ; locale résolue par requête.
- Emails, notifications, messages d'erreur **localisés**.

## Checklist d'implémentation
- [ ] `@nuxtjs/i18n` configuré (FR, EN), FR par défaut, détection navigateur.
- [ ] Aucune string en dur (lint/CI).
- [ ] `lang` sur `Idea`, `Iteration`, contenu ; traduction-à-la-lecture avec cache.
- [ ] Modèle d'embedding **multilingue** câblé pour tout ce qui alimente le matching.
- [ ] Locale passée dans l'état LangGraph → réponses agents localisées.
- [ ] `Accept-Language` respecté côté API ; formats localisés.
