# Acceptance evidence - verify-pilot-journey

The browser suite simulates every API response, so it proves what the browser renders and nothing about authentication, isolation, persistence or the worker. This change stands up an isolated local environment with its own identity provider and three synthetic identities (two members of one workspace and one non-member), runs the decision-space journey through the real browser, API, database and worker, and records what was observed. The pilot deployment was never touched, no customer data was involved, and authentication was never bypassed: every step ran under a real OIDC session issued by the local provider.

## Verification runs (2026-09-19)

Live, in production, after the deploy: not observed. This verification ran against an isolated local environment, not against the pilot, and the pilot was left untouched. Reading the journey on the deployed site belongs to the delivery comment.

Local, before deploy:

- Environment: `docker compose -f docker-compose.yml -f /Users/memo/.kollio-verify/verify.yml` with an isolated Logto on `http://localhost:33301` (its console on the same origin), three synthetic provider users (`admin`, `sam`, `outsider`) and their matching kollio accounts, and the repository's own Postgres, Redis, API, worker and web containers. The nine pivot migrations were applied through the API container.
- API checks: `uv run --project apps/api ruff check apps/api scripts` -> `All checks passed!`; `uv run --project apps/api ruff format --check apps/api scripts` -> `335 files already formatted`; `apps/api/tests/integration/test_experiments.py` -> `2 passed`; the full suite `uv run --project apps/api python -m pytest apps/api -m 'not live'` with a real `TEST_DATABASE_URL` -> `2 failed, 795 passed, 2 deselected in 273.40s`, both failures being environmental (`tests/e2e/test_agentic_runtime.py` left its workflow queued, a path this change does not touch, and `tests/performance/test_agent_validation.py` missed a 0.5 s CPU budget by 9 ms and passes when re-run alone).
- Browser journey: executed with the browser automation tooling against the running stack, the records read back from the database and from the pages after a full reload, the refusals probed from the non-member's own session, and the locales and the phone width checked as recorded in the table above.

## Known boundaries

- The committed browser suite still simulates the API; the journey evidence in this change is the manually driven run recorded here, not a test that CI repeats.
- Provider-dependent behaviour is not verified: no model gateway was started, so the Critic, the confrontation and the narrated analysis were not exercised.
- The verification outcome was recorded without an observation date. The date control refused tool interaction and the API accepts an empty `observed_at`; the value, unit and comment are present, the date is not.
- The non-member's refusal is observed at the API level (404 for reads and writes). The screen for that case renders an empty shell inside the workspace layout rather than an explained message, which is recorded as a UX observation: nothing leaks, but a person who follows a shared link sees a blank page instead of being told the space is not theirs.
- Two environment fixtures were needed and are recorded rather than hidden: the refresh-token rotation flag has to live in the OIDC client's `custom_client_metadata` for a server-rendered session to survive concurrent refreshes, and `Verificateur` was added to `decision_space_participants` by SQL because the frontend exposes no control for managing a decision space's participants even though the API has the route.
- The identity provider is a local Logto seeded for this run, not the pilot's. The journey therefore proves the product against a real OIDC provider, not against the exact provider configuration the pilot uses.
- Task 3.4 (tear down the environment) is left open: another agent session shares this checkout and the local stack, so the containers were left running. Every credential in it is throwaway, nothing from it is committed, and the secrets live outside the repository in `/Users/memo/.kollio-verify/.env` (mode 0600); `docker compose -f docker-compose.yml -f /Users/memo/.kollio-verify/verify.yml down` removes the local stack.
